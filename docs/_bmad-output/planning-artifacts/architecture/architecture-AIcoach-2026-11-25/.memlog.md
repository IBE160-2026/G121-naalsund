- (decision) Paradigm: modular monolith (FastAPI vertical slices identity / swings / coach / system, mirrored in Next.js modules) + analysis engine as a separate pure-Python package in pipes-and-filters style (ingest -> pose -> events -> measurements -> rules -> evidence), functional core with ports for pose and LLM. Prevents analysis logic leaking into web/db layers and breaking the FR-6 CLI.
- (decision) Dependency direction: engine imports nothing from app, db, web or LLM; app slices depend on engine; slices call each other only via service functions, never each other's tables; frontend reaches backend only via HTTP /api.
- (decision) Runtime topology adapted from technology.md: Docker Compose with proxy (Caddy, single origin, 0.0.0.0:8080 so a phone on Wi-Fi reaches it), frontend (Next.js standalone), backend (FastAPI + in-process analysis worker), db (Postgres 18), named volume for data. Dropped for MVP: Redis, Supabase, Railway, backup, watchdog, Cloudflare, payments, email, content-service tokens.
- (decision) Storage: local filesystem under DATA_DIR (Docker named volume, outside repo) behind a FileStore interface; Supabase Storage is the next-phase implementation. Paths derived from ids only: users/{user_id}/clips/{clip_id}/original.{ext} and playback.mp4; users/{user_id}/analyses/{analysis_id}/keyframes/{event}.jpg. User-provided filenames never used in paths.
- (decision) Analysis execution: DB-backed job state on the analyses row; one in-process worker task in the backend picks queued analyses oldest first and runs the engine in a ProcessPoolExecutor(max_workers=1); one analysis at a time. On startup running -> failed. Hard timeout 10 min -> failed. No Redis/Celery. Progress: worker writes steps; client polls GET /api/analyses/{id} every 1 s.
- (decision) Analysis status machine: queued -> running -> result | rejection | failed. Only failed -> queued (Try again re-runs on the stored clip; needs clip present). Fixed step ids pose, events, measurements, rules, explanation (UX step log). Ingest checks (decode, duration, fps) run inside step pose; a rejection records the step it stopped at; failed is a system error, never a rejection, never lists filming reasons. Resolves UX OQ1 and OQ9.
- (decision) Entities: User 1-* Clip, User 1-* Analysis, Clip 0..1-0..1 Analysis via analyses.clip_id (nullable, unique, ON DELETE SET NULL), Analysis 1-* ChatMessage; key frames are files owned by the analysis. Every row carries user_id; all reads/writes go through repository functions that require user_id; another player's id returns 404 not_found (FR-2).
- (decision) Delete coupling: delete clip keep analysis -> clip row + clip files removed, analysis.clip_id NULL (clip deleted row, key frames kept). Delete clip and analysis -> both rows + files. Delete analysis -> analysis row, key frames and chat removed, clip stays (Analysis deleted row). 50-clip limit = count of clip rows. DB transaction first, files removed after commit; startup sweep removes orphan files. Account delete cascades all rows and removes users/{user_id}/.
- (decision) Result document: one versioned Pydantic model AnalysisResult (defined in the engine, schema_version field) stored as JSON(B) in analyses.result; single source for result screen, explanation input and chat input. Holds per-fault outcome (verified/possible/absent), measurements with band, fault chain links, evidence items with stable ids, key-frame overlay geometry, observation, rule-table version hash, fps warning, step timings.
- (decision) Evidence ids assigned by the engine in AnalysisResult (E1..En, stable order); UI pin numbers, explanation and chat citations and Based-on footnotes all reference these ids. Nobody else numbers evidence.
- (decision) Rule table: config/rules.yaml, Pydantic-validated at startup and in the engine CLI; holds active faults + reserve (sway), potential/fault thresholds, confidence caps, causes, drills, mobility exercises + instructions, feel-cue and observation templates, extra-measurement list, jargon blocklist, medical notice. Engine takes it as input; no threshold or coaching copy constant in code. Swap OTT->sway = edit the active list.
- (decision) Confidence band computed only in the engine: composite of landmark visibility at key frames, margin from the deciding threshold, event-detection clarity (addendum C); caps applied last in one function (fps<120 never high; over the top max medium while hand-path proxy). UI and LLM never compute, change or raise a band.
- (decision) Pose port: PoseEstimator returns a canonical PoseSequence (own named-joint set, image-normalized x,y, visibility 0..1, per frame + timestamps). Implementation picked by week-1 spike: MediaPipe 1.2.x PoseLandmarker vs rtmlib RTMPose-m on onnxruntime; selected via POSE_BACKEND config. Only the adapter imports the pose library. Smoothing (6 Hz Butterworth) and body-relative units live after the port, shared by all backends.
- (decision) Event detection: EventDetector port; default Yamamoto wrist-height heuristic; SwingNet only as optional fallback adapter behind a flag, default off, listed for removal before paid launch (NFR-7).
- (decision) Video handling: server is the validation authority; client pre-check (format, duration) is advisory and uses limits from /api/config. ffprobe reads fps/duration/codec/rotation; OpenCV headless decodes only the trimmed swing window for pose; ffmpeg CLI (subprocess) makes an H.264 MP4 playback copy after the analysis ends (iPhone HEVC .mov does not play in Chrome/Android). Original kept for retry and re-tuning; both deleted with the clip.
- (decision) Upload: POST /api/clips multipart streamed to disk, max 300 MB (Caddy + backend). Format/length/library-full refusals return 4xx before any clip row is created (FR-5). Accepted upload creates clip row + queued analysis in one transaction and returns the analysis id. fps<30 or unreadable video -> stored rejection (FR-8).
- (decision) Key frames stored as plain JPEG stills; overlays (points, lines, arrows, dashed address line) are geometry in AnalysisResult in normalized image coords, drawn by the frontend as SVG per DESIGN.md. Server never burns overlays into images.
- (decision) LLM gateway: coach slice owns one CoachLLM port with explain(facts) and answer(facts, history, question); adapters OpenRouter via pydantic-ai (when OPENROUTER_API_KEY set) and Mock (deterministic templates / fixed sample answers). Input is a CoachFacts projection built only from AnalysisResult (no email, user id, clip, images). Model id from OPENROUTER_MODEL; tokens and cost logged per call to answer OQ2.
- (decision) Grounding check: one deterministic function for explanation, observation rephrase and chat: allowed fault/cause/drill/mobility names from the analysis, every number must exist in CoachFacts (unit-aware tolerance), cited evidence ids must exist, word limits (150 explanation, 80 chat), jargon blocklist, one feel cue per verified fault, no confidence raise, Based-on list from cited ids. Fail -> explanation/observation fall back to template; chat retries once then returns a fixed refusal. Explanation generated in the job explanation step; chat is a synchronous POST with 30 s timeout.
